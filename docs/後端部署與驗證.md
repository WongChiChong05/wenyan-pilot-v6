# 後端部署與驗證

日期：2026-09-21。架構：Next.js 伺服器路由 + Supabase PostgreSQL；建議部署到 Vercel。此文件不表示已建立雲端專案或已公開部署。

## 1. 為什麼採用這個架構

保留現有 Next.js 專案，不另外重寫 Flask 服務。瀏覽器只呼叫本站 API（Application Programming Interface，應用程式介面）；資料庫密碼與模型金鑰只在伺服器。

資料庫使用 `pg` 驅動直接連線到 Supabase 的 PostgreSQL。不是透過前端 Supabase SDK，不需把資料表公開给瀏覽器。

Vercel 是按請求執行的部署環境，不能把本機 `data/db.json` 當持久研究資料。正式環境若沒有 `DATABASE_URL`，儲存層初始化會拒絕請求；不會靜默改用暫存 JSON。

## 2. 本次新增的後端能力

- 五類資料：participants、responses、interactions、events、scales，位於獨立 `wenyan` schema（資料表命名空間）。
- 請求交易、受試者資料列鎖，以及前測分組的共用鎖。
- 唯一 token、每位受試者每階段每題唯一作答、每位受試者唯一量表；重複交卷保留原答案。
- 階段、選项範圍、請求大小、同來源、延遲開放窗、伺服器計時及舊互動提交驗證。
- 同時記錄作答與階段更新；失敗回復，不留下半次流程。
- 教材檢查通過與正式模型設定，是 `STUDY_MODE=collection` 建立受試者的必要條件。
- 模型重新生成、回退與理由判定的稽核紀錄。
- 資料庫建表、只向空庫匯入、本機備份及 CSV（Comma-Separated Values，逗號分隔表格）匯出工具。
- 正式 build 後檢查部署追蹤：包含 PostgreSQL 驅動，移除本機資料／備份的部署參照，不刪除原資料。

研究條件仍保留：三組、相同模型設定、目標句相同解釋、自願使用、不顯示目標底色、S2 最低 180 秒、延遲 +24 至 +48 小時、逾時留資料。

## 3. Supabase 設定

1. 由帳號持有人建立研究專案，選擇與部署伺服器接近的區域。本專案 `vercel.json` 設定 `sin1`（新加坡）；實際可選區域與方案依帳號確認。
2. 在 Supabase 的 Connect 取得連線字串。供短生命週期伺服器使用 transaction pooler（交易連線池，通常連接埠 6543）；建表可使用直接連線或 session pooler（工作階段連線池）。
3. 使用 TLS（Transport Layer Security，傳輸層安全協定）及憑證驗證。依連線端點與憑證設定 `sslmode=verify-full`；需要 CA 憑證時依官方方式設定，不以停用憑證驗證解決錯誤。
4. 密碼有特殊符號時依 URL 規則編碼。連線字串不要貼到聊天、截圖、Git 或前端環境變數。

來源：[Supabase 連線方式](https://supabase.com/docs/guides/database/connecting-to-postgres)、[連線池與限制](https://supabase.com/docs/guides/database/connection-pooling)。

在未存在 `.env.local` 時，由 `.env.example` 建立本機設定；若已存在，保留原檔，只修改需要的欄位。以下全部是範例，不是真實憑證：

```dotenv
DATABASE_URL=postgresql://使用者:密碼@連線池主機:6543/postgres?sslmode=verify-full
DATABASE_MIGRATION_URL=postgresql://使用者:密碼@建表連線主機:5432/postgres?sslmode=verify-full
STUDY_MODE=dry-run
LLM_PROVIDER=mock
LLM_MODEL=
ADMIN_PASSWORD=另產生的長隨機祕密
```

不要使用 `NEXT_PUBLIC_DATABASE_URL` 或 `NEXT_PUBLIC_GEMINI_API_KEY`。管理者祕密預設 `change-me` 會被拒絕。

### 建立資料表

```powershell
npm run db:migrate
```

正式來源是 [db/schema.sql](../db/schema.sql)，不是舊 `supabase/schema.sql`。建表工具有交易與 checksum（內容校驗碼），重跑同一版不重建資料；發現已套用內容遭修改會停止，不偷偷修改已有資料庫。

新表在 `wenyan`，不搬動或刪除既有 `public` 表。RLS（Row Level Security，資料列層級安全性）啟用，但伺服器資料庫角色為有權限的後端角色；RLS 不是拿來隔離同一伺服器金鑰的不同受試者，受試者隔離另靠 token 驗證與回傳欄位限制。

## 4. 先乾跑，再部署

本機先執行：

```powershell
npm test
npm run typecheck
npm run validate:content
npm run smoke
npm run build
```

教材檢查目前預期失敗。`npm run build` 可供工程乾跑建置；正式收案建置要用 `npm run build:collection`，它先檢查教材再建置。

在 Vercel 匯入此專案後，設定同樣的**伺服器端**環境變數，使用 Node.js 22.x（本機測試版本 22.14.0）。先設定 `STUDY_MODE=dry-run` 與 `LLM_PROVIDER=mock`，使用專用測試 Supabase。核對函式區域、執行時間與方案限制；不要把測試與正式收案放在同一資料庫。

`assist` 路由宣告最長 150 秒，供理由判定及生成重試使用。這是程式設定，不是對帳號方案執行時限的保證。來源：[Vercel 函式區域](https://vercel.com/docs/functions/configuring-functions/region)、[函式執行時間](https://vercel.com/docs/functions/configuring-functions/duration)。

真實模型設定需在供應商帳號確認可用模型，再固定 `LLM_PROVIDER`、`LLM_MODEL` 與金鑰。程式只檢查模型字串非空，**沒有證明它是有效或不可變的版本**。兩個 AI 組共用同一設定來源。

## 5. 進入正式收案的門檻

1. 人工完成教材校勘與簽核，`validate:content` 無錯誤。
2. 處理 [提示詞指南第 6 節](程式與提示詞審閱指南.md#6-收案前不得忽略的限制) 的設計問題，尤其自由選取第三層及理由退回次數。
3. 真實模型在乾跑庫通過人工語義、洩答與理由判定檢查。
4. 真實 Supabase 的連線、重新整理恢復、同時提交、匯出、备份恢復完成驗證。
5. 三組瀏覽器完整操作通過，包含時間到自動交卷、延遲窗口、網路失敗。
6. 封存教材、提示詞、依賴鎖定檔、Git 版本、部署識別、模型與分層切點。現有 `CONFIG.version` 是 v5.5，但不自動代表每一次程式修改。
7. 在**新正式資料庫**建表，以 `STUDY_MODE=collection` 和真實模型部署；不要將乾跑紀錄混入分析。

`collection` 的建立受試者端點會重用同一內容檢查器。通過該機械檢查仍不代表已完成倫理核可、內容專家審查或模型語義驗證。

## 6. 匯出、備份與既有資料

### 管理者 API

使用 `Authorization: Bearer <ADMIN_PASSWORD>` 標頭，不把密碼放在網址。正式環境不接受舊 `?key=` 寫法。

```text
GET /api/admin/export?table=participants
GET /api/admin/export?table=responses
GET /api/admin/export?table=interactions
GET /api/admin/export?table=events
GET /api/admin/export?table=scales
GET /api/admin/summary
```

匯出包含研究私密資料、登入 token 及原始模型回應，不應作為公開資料。摘要的既有分母與洩答指標限制見審閱指南；不能直接複製成論文統計。

CSV 保留原始文字以供分析，沒有把可能開頭為 `=` 等字元的內容改寫。用試算表開啟受試者自由文字時，應以純文字匯入並停用公式解讀，避免公式注入；需要公開資料時另做去識別與欄位刪減。

### 一致性快照

```powershell
npm run db:dump
```

在同一唯讀交易中擷取五張表，輸出到 `backups/時間戳/`，各有 JSON 與 CSV。此目錄已忽略於 Git。把備份移交至有存取控制的研究儲存位置；單純留在同一台筆電不是完整備援。

### 匯入原本 JSON

```powershell
npm run db:import -- data/db.json
```

只接受五表皆空的目標庫，整批在交易內處理，失敗回復；原檔不改動。缺乏歷史設定的列標成 `legacy-unrecorded`，不假造當時設定。這不是與已有正式紀錄合併的工具，也不會自動把乾跑資料變成有效受試資料。

## 7. 並行與安全限制

- 本機 JSON 只供單程序開發；同時兩個 Node 程序不受同一個記憶體佇列保護。
- PostgreSQL 每個程序最多三個連線，不是整個部署全域最多三個。實際容量仍受連線池與方案限制。
- AI 請求期間持有受試者列鎖，競爭操作最多等鎖 5 秒，之後回 409 要求重新讀狀態。這不是無限吞吐架構。
- PGlite 契約測試執行真實 SQL，但用單連線序列化，不能證明真實跨連線競爭行為。
- 若設 `TEST_DATABASE_URL` 再跑 `npm test`，會額外在**專用測試資料庫**建立各案例的隨機 `wenyan_test_*` schema 並於結束後移除。只刪該案例新建命名空間，不碰正式 `wenyan`；仍不要提供正式庫憑證。
- 未加入正式招募名額／邀請碼／全域濫用限流。公開受試入口前需限制招募範圍並設定平台流量防護，避免他人建立大量 session 或消耗模型費用。
- token 網址相當於登入憑證，不能貼公開截圖；需要正式資料保存期限與退出後資料處理規範，不能由程式代替研究者決定。
